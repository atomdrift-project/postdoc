Postdoc memory and throughput benchmarks

Build the production binary with `make release`. The default build includes
jemalloc profiling support; allocation sampling remains off unless enabled
with _RJEM_MALLOC_CONF at process startup. No extra debug tools are needed on
galadriel: jeprof and gdb are already installed.

Worker benchmark (includes HTTP download, staging, analysis, and result post):

  make worker-benchmark WORKER_BENCH_PATH=/var/tmp/triage \
    WORKER_BENCH_OUT=out/triage-before BENCH_BINARY=/path/to/baseline

  make worker-benchmark WORKER_BENCH_PATH=/var/tmp/triage \
    WORKER_BENCH_OUT=out/triage-after BENCH_BINARY=target/release/postdoc

Use SCAN_MODELS_DIR and CLEAVE_TRAITS_DIR to pin the model/rules inputs to the
same snapshots. XDG_CACHE_HOME selects the download/rule cache. The harness
disables persisted analysis results. It uses a loopback mock hopper adapted
from scan's benchmark, with no --data-dir shortcut, so staging allocations are
measured. It does not run an LLM. WORKER_BENCH_FETCH=all enables dependency
fetching and can contact external registries; the default, none, isolates the
top-level workload. Both runs must use the same fetch policy and worker count.

Each output directory must be new. It contains the input SHA-256 manifest,
binary hash and configuration, complete responses, verdict fingerprint,
worker RSS samples, and the mock hopper's per-size latency/throughput summary.
Compare fingerprint.json before accepting any timing/memory result. Analysis
errors are outcomes, not successful verdicts; inspect them even when the
worker exits successfully. Repeat A/B runs when shared-host load is variable.

For the 40% sample-throughput target, compare complete current-format worker
replays (including cgroup accounting) with:

  python3 scripts/compare-throughput.py out/before out/after \
    --target 1.4 --report out/throughput-comparison.json

This recomputes full content fingerprints from all retained responses and
requires identical outcomes, including errors. A 40% throughput gain means
wall time at most baseline / 1.4, about 28.6% shorter. Timing alone cannot
pass the comparison. Preserve input, model, and rule snapshots; repeat the
pair under comparable host load. Keep foreground and idle-worker modes
separate and collect CPU profiles in a separate diagnostic run.

For three runs per version, alternate before/after runs, then compare medians:

  python3 scripts/compare-throughput.py out/before-1 out/after-1 \
    --before-repeat out/before-2 --before-repeat out/before-3 \
    --after-repeat out/after-2 --after-repeat out/after-3 \
    --target 1.4 --report out/throughput-three-runs.json

All six replays must be complete and have matching full outcomes. The tool
also checks that the executable stays fixed within each version and that
worker, allocator, admission, asset paths, and tuning settings match. Preserve
asset content hashes separately and inspect the retained host-load samples.

Memory scope: peak_rss_mib is the worker process's VmHWM, sampled while it
runs. It excludes helper processes and filesystem memory. Benchmark extraction
uses output/scratch on disk to avoid competing with the production /tmp cap.
This is a heap/queue benchmark, not proof of a whole-service memory ceiling or
tmpfs performance. For production, also inspect the service's memory.current,
memory.stat (anon and shmem), memory.events, and /tmp occupancy.

A worker replay can also include helpers, tmpfs, and file-cache charges by
running it as the sole initial process in a dedicated cgroup. For example:

  doas systemd-run --unit=postdoc-bench-before \
    -p User=t -p WorkingDirectory="$PWD" -p MemoryMax=64G -p MemorySwapMax=0 \
    -p RemainAfterExit=yes -p TemporaryFileSystem=/tmp:rw,mode=1777,size=16G \
    --setenv=SCAN_MODELS_DIR="$PWD/out/bench-assets/models" \
    --setenv=CLEAVE_TRAITS_DIR="$PWD/out/bench-assets/traits" \
    --setenv=XDG_CACHE_HOME="$PWD/out/bench-cache" \
    python3 scripts/bench-worker.py CORPUS out/replay-before \
      --binary BEFORE_BINARY --workers 96 --max-rss-gb 54 --fetch all \
      --allocator-config retain:true,muzzy_decay_ms:0 \
      --scratch-root /tmp --measure-cgroup

Choose a new unit/output name for each run and the same resource settings for
both binaries. The private tmpfs keeps benchmark extraction separate from
other users of /tmp while retaining the production filesystem size. MemoryMax above reproduces the existing production idle-worker
cgroup; it is a benchmark setting, not a proposed new production cap. Poll
systemctl show UNIT -p SubState -p ExecMainStatus; systemd-run returns before
the benchmark finishes. Stop the transient unit after collecting its results.

--measure-cgroup refuses a shared cgroup at startup. memory.jsonl records
whole-cgroup current/peak memory, anon, shmem, file cache, kernel, and OOM
counters. summary.json retains these along with worker RSS. Per-type sampled
peaks can occur at different times, so do not add them together. Disk output
and input page-cache charges are included in file; shmem is a subset of file.
CPU counters include the worker and its helpers. Host CPU ticks and available
memory are sampled alongside them to identify interference from other jobs;
these counters do not replace repeated wall-clock comparisons.
--scratch-root creates a private directory and removes it after stopping all
benchmark processes. A failed/timed-out run writes failure.json with partial
progress; it is never represented as a completed benchmark.

Worker process_wall_s and the final cgroup snapshot are recorded before
fingerprint validation. harness_wall_s includes that later validation work.
An OOM event in the measured cgroup fails the run even if the worker exits 0.
Older artifacts without harness_wall_s included fingerprinting in their
process_wall_s; use their saved last-completion wall_ms for workload timing.

fingerprint-content.json hashes the full raw report (traits, evidence, facts,
member order) and ML output separately, excluding only ML analyzed_at. Compare
it as well as fingerprint.json's level decisions. Live registry responses can
change between fetch-enabled runs, so investigate differences before blaming
or accepting a code change. --fetch none fixes the local inputs, but evaluation
deadlines, helper timeouts, and nondeterministic evidence selection can still
change reports. Repeat the baseline and inspect changed fields; matching ML
decisions alone does not establish that all evidence was preserved. Do not
remove these fields from the content fingerprint to make a comparison pass.

A worker abort is not necessarily an OOM: preserve failure.json, worker.log,
and the service's memory.events, and inspect the assertion/signal before
interpreting its peak as a completed workload measurement. Keep a crashing
input as a separate reproducer while repairing the comparison; an incomplete
run cannot establish end-to-end throughput.

For a whole-service observation, including its foreground and idle child
cgroups, run (with doas when the service's cgroup is not readable):

  doas python3 scripts/monitor-memory.py out/service-memory.jsonl \
    --duration 1200 --interval 15

The output path must be new. Cgroup counters include helpers and tmpfs;
per-process RSS is additional attribution, not an additive accounting of
shared pages. Preserve both memory.stat and memory.events when diagnosing
OOMs. The inode identifies cgroup recreation across service restarts.

Worker prefetch_buffer_mb now measures reserved input space during download,
queueing, and admission waits. It is released when blocking analysis starts,
or when a cancelled/failed input is dropped. prefetch_buffer_budget_mb reports
the existing staging budget. Unknown HTTP lengths reserve their maximum until
the actual size is known, so reserved bytes can exceed current buffer length.
Analysis allocations remain governed by the separate admission mechanism.

Registry retention benchmark (Linux): put zstd-compressed raw registry JSON
documents in a fixture directory, then run the same fixtures/repetitions
against each dependency build:

  _RJEM_MALLOC_CONF=prof:false,retain:true,dirty_decay_ms:0,muzzy_decay_ms:0 \
    cargo run --release --features bench-hopper --example provenance-memory \
    -- out/registry-fixtures 4

This holds the generated provenance documents while measuring process RSS,
then encodes their capped upload sidecars. Compare upload_sha256 and document
counts as well as time and RSS. Keep fixture hashes and compiler/allocator
settings fixed. It measures this stage, not end-to-end service throughput.

Use worker-heap-benchmark with a distinct output directory to collect sampled
heap profiles. Sampling changes timing: never compare a profiled run's wall
time against an unprofiled run. Profiles are stored under output/heap, on disk.

HTTP server benchmarks are also available as server-benchmark and
server-heap-benchmark, configured with SERVER_BENCH_PATH, SERVER_BENCH_OUT,
SERVER_BENCH_WORKERS, SERVER_BENCH_PORT, and BENCH_BINARY. They use the v1 raw
upload protocol and accept its NDJSON progress stream. They do not exercise
the worker's hopper download/prefetch path.

Deterministic graft fixture

Build examples/graft-memory.rs against each dependency revision with the same
profile, saving the two executables, then run:

  python3 scripts/bench-graft.py BEFORE_FIXTURE AFTER_FIXTURE out/graft-pair

The fixture calls the public reference-outcome graft API on an archive with
512 members, 64 KiB of retained evidence per member, and eight declaring
members. It loads only tests/fixtures/graft-memory rules. Each run uses a fresh
process; the harness alternates order and requires complete report equality.
It records binary/rule hashes and every full report. allocated_bytes counts
cumulative caller-thread allocation requests during grafting, not live memory;
peak_rss_kib is the fixture's VmHWM with the system allocator. Its subsecond
timings need repetitions. Use the worker/cgroup benchmark above to establish
whole-service improvements with the production allocator and real workload.

Production profile symbolization

The executable must be the exact build captured in the profile. Keep its hash
and a copy before rebuilding. If production's mapped executable path differs
from the local binary, rewrite only that path in a COPY of the heap profile
before passing it to jeprof. Unresolved addresses do not identify callers.
jeprof's C++ name shortening also collapses many Rust methods into the same
name; retaining full demangled names avoids false attribution. Allocator
backtrace frames are common ancestors of sampled allocations, not evidence
that the profiler itself owns all the attributed memory.

Foreground replay without idle work (Linux)

Benchmark foreground serving and the idle worker separately. Run the server
harness from outside its measured cgroup. It starts the real server without
hopper, verifies the idle worker is off, and streams a foreground batch:

  python3 scripts/bench-service.py FOREGROUND_DATASET out/foreground-before \
    --binary out/memory-baseline/postdoc-combined-memory \
    --models out/bench-assets/models --traits out/traits-catch-fixed \
    --cache out/bench-cache --workers 192 --clients 20 \
    --memory-gb 64 --max-rss-gb 54 --tmp-gb 16

The dataset must contain unique content hashes. Keep the inputs, asset
snapshots, resource settings, and client count fixed between runs.
Fetch/follow and analysis-result caches are disabled. The harness does not
contact production hopper. Its load generator stays outside the measured
transient unit; postdoc and its helpers remain inside it. The unit is stopped
on success or failure. Run the worker-only replay above in a separate phase.

memory.jsonl records the server cgroup. summary.json retains the kernel
cgroup peak and foreground wall time. foreground-fingerprint.json contains
full report hashes for exactly the input roots. Any missing result, analysis
error, unexpected idle worker, or OOM event fails the run.

Separate benchmarks establish memory and throughput for each mode. Observe
the production cgroup separately to attribute the live service's total memory;
the idle worker can retain allocations while frozen during foreground work.

When benchmarking on a machine serving production traffic, keep its companion
idle worker paused too; disabling idle work only in the benchmark server does
not remove the other worker's CPU and memory-bandwidth load. Restore production
idle work after the timed run. Record that pause with the benchmark settings.

Large TAR member fixtures

  python3 tests/fixtures/archive-memory/make-corpus.py out/archive-memory-data

This streams a large zero-run member with nonzero evidence markers, a dense
member, and a truncated large member into compressed archives. It never writes
the expanded members. The sibling manifest records expected full member hashes
and lengths. Pass --large-mib 129 for quick correctness checks; the default
8.5 GiB member exercises the geometric buffer growth found in a production
archive. Replay this corpus with the worker harness above and compare complete
reports. Include cgroup memory: jemalloc profiles omit anonymous mappings.
Check the full workload separately before accepting memory or timing claims.

Linux host memory samples retain raw MemAvailable and report OpenZFS ARC
separately. Benchmark guards may credit half the clean, evictable ARC above
its kernel floor, capped at 64 GiB, after subtracting memory already included
in KReclaimable. They retain a 16 GiB effective reserve and stop below 4 GiB
raw MemAvailable. This changes benchmark accounting only; application cgroup
limits and ZFS cache settings stay fixed. Both versions must use the same
guard policy, and cgroup peaks still include the application's actual memory.

For production worker-only tuning, POSTDOC_IDLE_CLEAVE_CONCURRENCY sets the
idle child's heavy-analysis gate. The server forwards it to that child as
SCAN_CLEAVE_CONCURRENCY; request concurrency and idle download slots retain
their own settings. A standalone worker replay uses SCAN_CLEAVE_CONCURRENCY
directly. Validate memory and full-workload wall time before choosing a value.

Linux Rizin launch cost

Filefacts can launch Rizin through setpriv, sh and prlimit when the scanner's
RSS reaches 512 MiB. Each utility execs the next stage in the same process;
the scanner can then use its normal spawn fast path without duplicating its
large address space. The chain preserves the private process group, parent
death signal and race check, scrubbed environment, and existing 4 GiB address
space/data limits, including tighter inherited limits. Small callers keep the
native child hook. Missing or incompatible utilities also use that hook.

The utility chain is checked once with a bounded trusted no-op. Containment
tests query the exec'd process's limits and signal, exercise parent exit,
and preserve literal arguments. CPU sampling belongs in a separate run or
after an explicitly retired timing window. perf's inclusive fork/exec costs
include their page-table copying/unmapping children; avoid adding those leaf
percentages again. Keep the exact sampled executable for symbolization.

Throughput investigation wrap-up (2026-10-22)

The 40% goal was not established. On the frozen 404-input worker corpus,
the original baseline took 1642.66 s. The best experimental tuning screen
took 1290.20 s (+27.3% throughput), with a 41.37 GiB whole-cgroup peak and
no OOM events. It used the scoped native Rizin indexes and a 64-thread
global pool, with inner/nested owner caps of 4/64. These settings and native
prototypes have not been deployed or integrated into the default runtime.

A separate 16-thread member-model pool took 1326.42 s and peaked at
38.31 GiB without OOMs. Its lower peak came with 2.8% longer wall time than
the best screen, so it was not integrated. Both screens completed all inputs
and retained the same one known malformed-input error. These are individual
measurements, not a successful three-pair acceptance result.

The best screen still has strict report differences, including independently
reproduced baseline nondeterminism. Evidence normalization, accurate deadline
diagnostics and deterministic stng fragment ordering remain separate source
prototypes; their combined application validation is unfinished. Do not waive
these differences or claim full output parity. Reviewed outcome improvements
are permitted, but the observed nondeterminism must be fixed before acceptance.

The workspace retains the validated overlapping prefetch implementation:
10 prefetch tests, formatting and strict all-target postdoc Clippy passed.
The benchmark memory-accounting and comparison helpers passed 14 Python
tests. The model-pool experiment separately passed 20 pipeline tests and
strict postdoc Clippy; that is functional evidence, not a throughput win.

At wrap-up all experiment processes were stopped and the private benchmark
tmpfs was released. Saved reports and source prototypes remain under
out/throughput; wrapup-results.json records their scope and remaining work.
System /tmp remains a 16 GiB tmpfs with hourly regular-file cleanup after
12 hours of inactivity. Sockets and other non-regular files are excluded.
The production service was left inactive, as before this final screen; its
configured MemoryMax remains 128 GiB. The 48 GiB backstop applied to these
benchmarks and is not a newly installed production limit.
